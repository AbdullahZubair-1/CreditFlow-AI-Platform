# Architecture & Engineering Notes

This is the deep-dive companion to [README.md](README.md) — full per-service architecture, every real bug found and fixed along the way, the reasoning behind each design decision, and the slice-by-slice build/verification history. Start with the README for a quick overview and setup instructions; come here when you need the details behind a specific service or decision.

---

Multi-tenant, credit-based SaaS platform for AI-assisted content generation and social publishing, built as independently deployable FastAPI microservices behind a single API Gateway, communicating over RabbitMQ, with Redis for caching/session state/rate limiting and a shared Postgres instance (one schema per service).

This repo was built incrementally, slice by slice, rather than all 13 services at once.

- **Slice 1**: signup → email verification → login → JWT issuance → account creation → account switcher, through the Gateway, consumed by a minimal React frontend.
- **Slice 2**: Billing Service — Stripe sandbox subscriptions/checkout/refunds via the transactional outbox pattern, with the Gateway now doing real Stripe webhook verification + relay instead of a 501 stub.
- **Slice 3**: Credits/Marketplace Service — append-only credits ledger, credit grants on `invoice.paid`, refund clawbacks, and peer-to-peer marketplace listing/purchase settled through a one-time Stripe Checkout Session that Billing creates on Credits' behalf.
- **Slice 4**: Usage/Metering Service — Redis quota counters for fast pre-checks, a durable Postgres usage ledger reconciled against Redis every minute, and 80%/100% threshold detection. Introduces the `ai_events` exchange that the (not-yet-built) AI Generation Service will publish to.
- **Slice 5**: AI Generation Service — Groq streaming completions (the spec names OpenRouter; this project uses Groq instead, same OpenAI-compatible shape) fanned out over Redis pub/sub, re-streamed to the frontend as SSE through the Gateway (now a real relay instead of a 501 stub), gated by a synchronous call to Usage's precheck endpoint, plus bonus Pollinations.ai image generation.
- **Slice 6**: Content Service — versioned draft/approved/published content, auto-created from `ai.generation_completed` (finally closing the loop AI Generation's events opened), manual image upload to a local-volume dev stand-in for S3.
- **Slice 7**: Scheduler Service — Celery + Celery Beat calendar (three containers: REST API, worker, beat, sharing one image), a Redis-locked periodic scan that fires due posts and emits `content.scheduled`, plus the bonus recurring-schedules feature (daily/weekly/monthly cadences).
- **Slice 8**: Social Publishing Service — LinkedIn OAuth 2.0/OIDC connect flow, encrypted token storage, consumes `content.scheduled` to publish text or text+image UGC posts (the bonus image-publishing feature), a token-refresh background job, and Gateway support for a truly public OAuth callback route.
- **Slice 9**: Scraper Service — the first MongoDB-backed service, Playwright-driven crawling with robots.txt compliance and per-domain rate limiting, an internal (non-Celery) recurring-scan loop, RabbitMQ job queue (`scrape.requested` → `scrape.completed`/`scrape.failed`).
- **Slice 10**: Notification Service — consumes nearly every domain event across the platform (across four separate exchanges) to send real transactional email via Resend, finally replacing the dev-only OTP/verification-token logging from Slice 1. Also fixes a real security gap found while wiring this up: the Gateway's catch-all proxy routes would have happily forwarded a public request straight through to any service's new internal-only `/internal/*` endpoints.
- **Slice 11** (final backend service): Admin/Ops Service — live Redis session listing/revocation, a cross-service per-account overview, and an audit log consuming literally every exchange in the platform (topic-bound `#`). Introduces a genuine platform-level SuperAdmin concept (a new JWT claim, independent of the account-scoped `role` every other service already used) and four small `/internal/*` aggregation endpoints on other services to support it.
- **Slice 12**: Frontend fill-in — every remaining spec page (Owner Dashboard, Team Management, Billing & Invoices, Credits & Marketplace, Content Studio with real SSE, Calendar, LinkedIn Connections, SuperAdmin Console), plus the Slice 1 placeholder-`account_id` fix nearly all of it depended on.
- **Slice 13**: Reliability hardening pass — a platform-wide audit for the one restart-safety gap the shared `processed_events` idempotency check can't close on its own (a crash between a handler's own commit and `mark_processed`), finding and fixing five real duplication/false-failure bugs.
- **Slice 14**: Post-launch hardening — two further spec-compliance audits closing real functional/security gaps (real credit debiting, role enforcement, token-leak fixes, CI), a critical transactional-outbox bug that had silently broken all cross-service billing sync, Stripe API-version compatibility fixes, a 7-day/95% refund policy with auto-downgrade, plan-gated features, a 50-credit signup bonus, and finally a production-style deployment behind nginx + ngrok.
- **Slice 15**: a permanent public URL (ngrok's static domain, pinned) and a real, working LinkedIn redirect; a dedicated SuperAdmin UI and an undeletable SuperAdmin account; email delivery switched from Resend to SMTP after hitting Resend's real single-recipient sandbox limit; login now actually enforces email verification; refund/marketplace/credit-purchase emails; an optional automatic web-research toggle in Content Studio (Wikipedia-backed, since general web search has no practical no-API-key option); and the calendar finally shows what was actually scheduled, not just when.

### Billing Service notes

- **Transactional Outbox**: every domain-event-worthy DB write (invoice recorded, subscription updated, refund issued) inserts an `outbox_events` row in the *same transaction*. A background poller (`app/outbox.py`, started in `main.py`'s lifespan) picks up unpublished rows every 2s, publishes them to the `billing_events` exchange with publisher confirms, and marks them published — so a crash between the DB write and the publish can never lose or double-emit an event.
- **Webhook flow**: the Gateway verifies the Stripe signature, deduplicates by Stripe event id (Redis `SETNX`, 24h TTL), and relays the raw event onto a `webhook_events` topic exchange with routing key `billing.<stripe event type>`. Billing consumes `billing.#`, persists every event to `subscription_events` *before* any further processing (per the reliability requirements), then updates `invoices`/`subscriptions` accordingly.
- **Stripe credentials are placeholders by default** (`sk_test_placeholder`, `price_pro_placeholder`, `price_team_placeholder`, `whsec_placeholder` in `.env.example`) — the checkout/webhook code paths are fully wired but only actually reach Stripe once you drop in real test-mode keys and Price IDs from your own Stripe sandbox account, and register a webhook endpoint (or run `stripe listen --forward-to localhost:8080/webhooks/stripe`) to get a matching `STRIPE_WEBHOOK_SECRET`. This repo's own `.env` (gitignored) has been running against a real Stripe test-mode account since Slice 14.
- **Dunning is fully implemented**: `invoice.payment_failed` records a `grace_period_ends_at` on the subscription row and emits `payment.failed` (`app/events.py`); `app/dunning.py` runs a plain in-process `asyncio` loop (started in `main.py`'s lifespan, scanning every `DUNNING_SCAN_INTERVAL_SECONDS`) — the same lightweight pattern Scraper's own recurring-scan loop uses, not the dedicated Scheduler Service — that finds every `status="past_due"` subscription whose grace period has elapsed with no successful payment in between, downgrades it to `plan_tier="free"`, and emits `subscription.downgraded` via the outbox. A successful `invoice.paid` in the meantime clears `grace_period_ends_at` and cancels the timer. `POST /billing/refunds` reuses this exact same downgrade shape (see "Refunds" below).
- **Refunds are policy-gated, not unconditional** (`app/config.py`'s `REFUND_WINDOW_DAYS = 7`, `REFUND_RATE = 0.95`): `POST /billing/refunds` rejects invoices older than 7 days and any invoice already refunded, then refunds exactly 95% of the charge (the remaining 5% is a retained processing fee, stated explicitly in the frontend's confirmation dialog). A successful refund also cancels the Stripe subscription and downgrades the account to Free, publishing `subscription.downgraded` through the same path dunning uses — a refund without this would leave the account on its paid tier until the next `invoice.paid` webhook silently un-did the refund's intent. `GET /billing/invoices` reports each invoice's real `refunded_amount_cents` (one grouped query against `refunds`, not N+1) so refund status survives a page reload and is consistent for every viewer, not just whoever clicked the button.
- **Stripe's 2025-03-31 "Basil" API version broke two assumptions this code originally made**, both found while wiring up refunds against a real account: (1) `Invoice.payment_intent` was removed outright (an invoice can now have multiple partial payments), so the payment intent is now resolved via `stripe.Invoice.retrieve(..., expand=["payments.data.payment.payment_intent"])` instead; (2) a proration invoice (switching plans) always carries multiple line items with the old plan's negative credit line ordered *before* the new plan's positive charge line — code that blindly read `lines[0]` silently detected the wrong plan on every plan switch. `_plan_tier_from_invoice_lines` now prefers the highest positive-amount line.
- **Plan switches charge immediately**: `PATCH /billing/subscription` uses `proration_behavior="always_invoice"` (was `"create_prorations"`, which only queues the price difference onto the *next* regular invoice) so Stripe generates and attempts payment on the prorated difference as part of the same API call — both the plan unlock and its credit grant are driven by that invoice's `invoice.paid` webhook, so deferring the charge silently deferred both.
- **The transactional outbox had a critical envelope bug, now fixed**: `app/outbox.py`'s poller originally published the raw domain payload dict directly, but every consumer (User/Tenant, Credits, Usage) expects the standard `{event_id, event_type, occurred_at, data}` envelope and reads `payload["data"]`/`payload["event_type"]` — meaning every `invoice.paid`, `refund.issued`, `subscription.updated`, and `marketplace.payment_completed` event published since Billing existed was silently unroutable by every consumer. In practice this meant a real, paid plan upgrade never unlocked paid-plan features or granted its monthly credits, and a real "buy extra credits" purchase never credited the ledger — the single most impactful bug found this session, since it broke cross-service sync for nearly every billing-driven feature at once. Fixed with a `_envelope()` helper wrapping each `OutboxEvent` row before publishing.

### Credits/Marketplace Service notes

- **Ledger is append-only**: `credits_ledger` rows are never updated or deleted; each row's `balance_after` is the running balance, computed once at write time from the previous row rather than a separately-mutated counter.
- **Credit grants**: consuming `invoice.paid` looks up `PLAN_CREDIT_GRANTS` (placeholder: `pro`→1000, `team`→5000, `free`→0) by the `plan_tier` Billing includes in that event's payload, and appends a `purchase_grant` ledger row. `refund.issued` claws back the same amount (capped at the current balance, so a refund can never take an account negative if the credits were already spent — a documented simplification rather than a hard error).
- **Marketplace settlement flow**: an account lists surplus credits (`POST /credits/marketplace/listings`, balance-checked but not locked — a known race-condition simplification noted in the code); a buyer calls `POST /credits/marketplace/listings/{id}/purchase`, which has Credits call **Billing directly** (service-to-service, bypassing the Gateway) at `POST /checkout-sessions/one-time` to create a real one-time Stripe Checkout Session for the listing price, tagged with metadata identifying the listing/buyer/seller. Billing's webhook consumer recognizes `checkout.session.completed` events carrying that metadata and emits a `marketplace.payment_completed` domain event (via its outbox) instead of treating it as a subscription event; Credits consumes that to atomically debit the seller and credit the buyer in one transaction, guarded by the listing's `pending_payment`→`sold` status transition so a duplicate webhook redelivery is a no-op.
- **No real payout to the seller**: the buyer's payment is real (Stripe Checkout, test mode), but nothing here transfers money to the seller's bank account — that needs Stripe Connect (connected accounts + transfers), which is out of scope for this slice's placeholder Stripe setup. The seller's ledger is credited with platform credits, not cash; documented here the same way the dunning-downgrade gap is in Billing.
- **Event publishing here is best-effort, not outboxed**: unlike Billing, Credits publishes `credits.credited`/`credits.debited`/`credits.low_balance` directly after committing the ledger write, with a try/except that logs and moves on if RabbitMQ is unreachable. The spec's Transactional Outbox requirement is scoped explicitly to the Billing Service; the ledger write itself (the source of truth) is still fully committed and correct even if a notification is dropped.
- **Found and fixed while building this slice**: the Gateway's Stripe webhook relay and Billing's webhook queue binding originally used the AMQP topic pattern `billing.*`, which only matches a routing key with exactly one word after `billing.` — but Stripe event types are themselves dot-separated (`invoice.paid`, `checkout.session.completed`), so the actual relayed keys have 2-3 segments and `billing.*` was silently matching **nothing**. Fixed to `billing.#` (matches zero or more words) in both places.
- **New accounts get a one-time 50-credit signup bonus** (consumes `account.created`), which can never be listed on the marketplace — `get_sellable_balance()` treats the bonus as a protected floor and `create_listing` enforces it server-side, so a new user can try the product without being able to immediately cash the welcome credits out to someone else.
- **Direct credit purchases, independent of subscribing to a plan**: `POST /billing/credits/checkout-session` computes the price server-side (`$0.09`/credit, from `credits_amount` alone — never a client-supplied total) and creates a one-time Stripe Checkout session; completion emits `credits.purchase_completed` for Credits to grant, idempotent via the Stripe checkout session id. `GET /credits/plan-grants` exposes Pro/Team's actual monthly grant amounts so the frontend can show both ways to get credits ("buy directly" vs. "included with your plan") in one place. Marketplace listings are capped server-side at 5% below this official rate, so undercutting the platform's own price by more than a token amount isn't possible.
- **A previously-public internal endpoint was hardened**: `POST /internal/checkout-sessions/one-time` (Billing, called by Credits to settle a marketplace sale) trusted a fully caller-supplied `amount_cents` + metadata with no `/internal/*`-path protection — reachable through the Gateway despite its name, which would have let a bad actor claim any purpose/amount combination for whatever price they chose. Moved behind the same `_reject_internal_paths()` mechanism every other service's internal endpoints already use.
- **A real balance-ordering bug was found and fixed while manually granting a missed credit purchase**: `get_balance()`'s tie-break on same-timestamp ledger rows sorted by a random UUID, which could pick the wrong "latest" `balance_after` when an account received two ledger entries in one transaction. Changed to sum all deltas instead, which is order-independent by construction.
- **Now genuinely debits credits, not just usage tokens**: consuming `ai.generation_completed` was previously wired only into the Usage Service's token quota — Credits never actually spent anything from the ledger for a generation, meaning the credit balance shown on the dashboard was disconnected from what generations actually did. Credits now debits the ledger on the same event, so "credits" and "usage" are both real, complementary meters instead of one being a fully synthetic dial.

### Usage/Metering Service notes

- **Quota model is a placeholder**: per-plan-tier *monthly token* quotas (`PLAN_TOKEN_QUOTAS`: free 50k, pro 500k, team 2M) are tracked independently of the Credits Service's credit balance — Usage meters volume/rate, Credits meters spend. Whether these two should eventually be unified (e.g. quota derived from remaining credit balance instead of a separate token budget) is a product decision left open for a later pass.
- **Two data stores, reconciled**: Redis (db 1, separate from the Gateway/Auth's rate-limit/jti Redis usage on db 0) holds the live per-account-per-month token counter that `POST /usage/precheck` reads synchronously; Postgres's `usage_ledger` is the durable, append-only source of truth written when `ai.generation_completed` is consumed. A background loop (`app/reconciliation.py`) recomputes each active account's Redis counter from the Postgres ledger every 60s, so a crash between the ledger write and the Redis increment self-heals within one interval rather than drifting forever.
- **This slice has no producer yet**: it consumes from a new `ai_events` exchange (routing key `ai.generation_completed`) that nothing publishes to until the AI Generation Service slice exists — the consumer, queue, and DLX are all live and correctly bound, just idle. `subscription.updated` (from Billing's existing outbox) already has a real producer, so the plan-tier cache populates correctly today.
- **Threshold detection is idempotent per period**: crossing 80% or 100% of quota emits `usage.threshold_reached` exactly once per `(account_id, period, threshold)` via a unique-constrained `threshold_flags` table — redelivery of the same `ai.generation_completed` event (caught earlier by the standard `processed_events` idempotency check) can't double-fire it, and neither can two generation calls in the same period that both push usage past 80%.
- **The plan-tier cache only listened for upgrades, not downgrades, until Slice 14**: the local `AccountPlan` cache `app/quota.py` reads from (rather than making a live cross-service call on the hot precheck path) was only ever bound to the `subscription.updated` routing key — `subscription.downgraded` (fired by Billing's dunning scanner, and later by a refund) was never bound at all, so a real account correctly downgraded everywhere else silently kept showing its old, higher-tier quota indefinitely. Fixed by binding the missing routing key to the same handler (renamed `_handle_subscription_updated` → `_handle_plan_changed`, since it already read a generic `{account_id, plan_tier}` shape shared by both event types — no logic change needed).

### AI Generation Service notes

- **Groq instead of OpenRouter**: the platform spec names OpenRouter as the text AI provider; this project uses [Groq](https://console.groq.com) instead — same OpenAI-compatible streaming chat completions shape, just a different host, key, and model catalog (Groq's is also known for very fast inference). A real key from [console.groq.com/keys](https://console.groq.com/keys) is needed to actually reach a model; the placeholder (`gsk_placeholder`) lets the service boot and fail gracefully instead. Two model choices are pre-configured and selectable by key name (`"fast"`/`"quality"`) rather than a raw Groq model slug, so the frontend never has to know the underlying slug.
- **The original models were fully retired from Groq's catalog mid-session**: `llama-3.1-8b-instant`/`llama-3.3-70b-versatile` started 404ing on every request; replaced with Groq's current production models, `openai/gpt-oss-20b` (`"fast"`, and also the `UTILITY_MODEL` for title/image-prompt generation) and `openai/gpt-oss-120b` (`"quality"`). Both are **reasoning models** — they spend part of their token budget on an invisible `reasoning` field before ever writing to the visible `content`, which is not how the original prompt/`max_tokens` tuning was designed. Every Groq call now sets `reasoning_effort: "low"` to cut wasted reasoning tokens, and the two short utility completions (image prompt, title generation) had their `max_tokens` raised well above their old non-reasoning-tuned values so they reliably survive the reasoning overhead instead of returning empty content with `finish_reason="length"`. `generate_image_prompt`'s empty-completion fallback is also now capped at 200 characters (was the entire, unbounded post body) — an empty completion previously produced a "prompt" long enough to blow past the image URL's DB column, crashing the request outright.
- **Streaming path**: `POST /generations` synchronously calls Usage's `/precheck` first (rejecting with `429 quota_exceeded` if over quota), then creates a `generation_jobs` row and kicks off a FastAPI `BackgroundTask` that streams from Groq, publishing each token to a Redis pub/sub channel (`generation:{job_id}`) as it arrives. The Gateway's `/sse/{job_id}` subscribes to that same channel and re-streams it to the browser as Server-Sent Events — the Gateway never talks to Groq directly, it's a pure relay.
- **EventSource can't set headers**: browsers' native `EventSource` API has no way to attach an `Authorization` header, so `/sse/{job_id}` is the one Gateway route that also accepts the access token via `?access_token=` query string (see `require_jwt_from_header_or_query` in `services/gateway/app/identity.py`) — every other protected route still requires the header only. The Gateway also confirms the caller actually owns the job (via AI Generation's existing per-account-scoped `GET /generations/{job_id}`) before subscribing, even though `job_id` is an unguessable UUID.
- **Known race, not fully solved**: a generation's background task can in principle start publishing tokens before the frontend's SSE `EventSource` has finished subscribing, since Redis pub/sub delivers only to subscribers already attached with no replay buffer. In practice Groq's network round-trip (Groq is fast, so this window is narrow) means this hasn't been observed to matter, but it's a real gap, not a proven-safe design — a fix (e.g. buffering early tokens in a short-lived Redis list until first subscriber attaches) is a candidate fast-follow if it turns out to matter.
- **Cancellation** is cooperative: `POST /generations/{job_id}/cancel` just sets a Redis flag; the streaming loop checks it between chunks and stops, persisting whatever partial response had accumulated with `status=cancelled`. There's necessarily a small window where a chunk already in flight from Groq still gets published after cancellation is requested.
- **Bonus image generation**: `POST /generations/{job_id}/image` hotlinks a Pollinations.ai URL (no API key, no upload step) rather than downloading and re-hosting the image — the Content Service (a later slice) will decide whether to keep hotlinking or mirror images into object storage.
- **Placeholder pricing**: `cost_cents` is a flat illustrative 1¢ per 100 tokens (`CENTS_PER_100_TOKENS` in `app/generation.py`) — Groq's real per-model rates vary widely and aren't wired up, same treatment as Billing's plan prices and Credits' grant amounts.
- **Event publishing here is best-effort, not outboxed** — same tradeoff as Credits: the `generation_jobs`/`prompt_history` rows are the committed source of truth; a dropped `ai.generation_completed` publish just delays Usage's ledger entry for that call rather than losing anything permanently.
- **Optional web research (Slice 15)**: `CreateGenerationRequest.use_web_research` triggers a best-effort call to Scraper's `POST /internal/research` (see Scraper's notes below), folding the result in as context ahead of the user's prompt before it reaches Groq — see Slice 15's "Content Studio: optional automatic web research" section for the full design and the real reason it's Wikipedia-backed rather than general web search.

### Content Service notes

- **`purpose` and `response_text` were added to `ai.generation_completed` retroactively**: Slice 4 (Usage) and Slice 5 (AI Generation) shipped before Content existed, and Content needs the actual generated text plus a way to tell "this was meant to become a post" apart from other future generation purposes (ad-hoc chat, etc.) — neither was in the original event payload. `CreateGenerationRequest.purpose` (default `"post"`) and the full `response_text` were added to AI Generation's request schema, `GenerationJob` model, and completed-event payload; Usage's existing consumer ignores the new fields harmlessly (additive, non-breaking).
- **Versioning is append-only**: every edit (including image uploads) increments `content.version` and inserts a new `content_versions` snapshot rather than mutating history — `GET /content/{id}/versions` returns the full timeline.
- **Publish permission is role-gated**: only `owner`/`admin` can move content between `draft`→`approved`→`published` (and back to `draft`); any member can create/edit drafts. The allowed-transition table (`draft→approved`, `approved→published`, `approved→draft`, `published→draft`) is enforced server-side in `app/api/routes.py`, not just hinted at by the frontend.
- **Local-volume "object storage"**: `POST /content/{id}/image` (multipart) writes to a Docker volume mounted at `/app/uploads` and serves it back at `/uploads/{filename}` via a `StaticFiles` mount — explicitly a dev stand-in for S3 (see `app/storage.py`'s docstring); swapping in real S3 later only touches that one file.
- **Draft creation is idempotent by construction**: the `ai.generation_completed` consumer checks for an existing `Content` row with the same `source_generation_job_id` before creating one, on top of the standard `processed_events` idempotency check — belt-and-suspenders against redelivery.
- **AI-generated images now auto-attach**: AI Generation publishes `ai.image_generated` after its bonus image action completes; Content consumes it and attaches `image_url` to the draft already created for that `generation_job_id` — closing a real gap where only the frontend's own follow-up `PATCH` (working only for that one browser session) made the image visibly attached at all.
- **AI output is now plain text, not Markdown**: Groq's instruct-tuned models default to Markdown (headers, `**bold**`, numbered lists), which rendered as literal asterisks/hashes once posted to LinkedIn. A system prompt now asks for plain text, and any Markdown that slips through anyway is stripped as a safety net on the persisted/published text. Draft titles are derived from the actual generation topic (also stripped of any leftover setext-style `===`/`---` header underlines) instead of the first raw line of the response.
- **A real `MissingGreenlet` crash blocked every content update**: `Content.updated_at` is server-generated (`onupdate=func.now()`); without `eager_defaults=True`, SQLAlchemy's async ORM marks it "expired" after an `UPDATE` and only lazily reloads it on next synchronous access — which isn't awaitable outside SQLAlchemy's own internal await chain, and crashes. This hit `update_content()` on every call (snapshot a version, commit, then rebuild the response from the same object), breaking both the Content Studio Edit feature and attaching a generated image to a draft. Fixed by setting `eager_defaults=True`, which fetches server-generated columns back via `RETURNING` in the same round trip instead of leaving anything to reload lazily.
- **Deleting content with version history originally failed outright**: `content_versions.content_id` had no `ON DELETE` behavior, so `DELETE /content/{id}` threw a `ForeignKeyViolationError` on any draft that had ever been edited. Snapshots are meaningless without the content they version, so the constraint now cascades.
- **`published` is now only reachable by a real LinkedIn post actually succeeding**: the Content Studio's old "Publish" button just flipped the status column with nothing actually posted anywhere. Social Publishing's `post.published` event now carries `content_id`, and Content consumes it to flip status to `published` only once Social Publishing confirms the real post — `update_status`'s manually-allowed transitions no longer include `published` at all, so the REST endpoint itself can't be used to fake it either. Content is only genuinely publishable via Calendar → Scheduler → Social Publishing → LinkedIn now, matching what "published" is supposed to mean.
- **Read and Edit actions were missing from Content Studio's Drafts list** in the original frontend fill-in — added alongside a version-history viewer (`ContentVersionHistoryModal`) driven by the already-existing `GET /content/{id}/versions` endpoint, which previously had no UI consumer at all despite the backend supporting it since Slice 6.

### Scheduler Service notes

- **Three containers, one image**: `scheduler` (the REST/calendar API), `scheduler-worker` (a Celery worker), and `scheduler-beat` (Celery Beat, which enqueues a scan task every 60s per `settings.beat_scan_interval_seconds`) all build from `services/scheduler/Dockerfile` — only the `command:` differs per container in `docker-compose.yml`. Celery's broker and result backend are Redis db 2, kept separate from the Gateway/Auth/AI-Generation's db 0 and Usage's db 1, per the spec's explicit call-out for this service.
- **Recurring schedules (bonus)**: `recurrence` is one of `none`/`daily`/`weekly`/`monthly`. A recurring post's `publish_at` advances by a fixed `timedelta` (`RECURRENCE_DELTAS` in `app/tasks.py`) each time it fires and stays `status=scheduled` for its next occurrence, rather than moving to `fired` like a one-off. `monthly` is a placeholder 30-day interval, not calendar-month-accurate (no Feb-28-vs-31st handling) — good enough to demonstrate the feature, not production calendar math.
- **Double-fire protection**: before firing, the task tries a Redis `SET NX EX` lock keyed on `(scheduled_post_id, publish_at)` with a 55s TTL — shorter than the 60s scan interval, so a lock can never outlive the window where the next scan would need it. This protects against both an overlapping slow scan and, if ever scaled beyond one, multiple beat/worker replicas.
- **`content.scheduled` publish failures are NOT swallowed here** — a deliberate exception to this codebase's usual "best-effort, log and continue" pattern for non-Billing event publishing (see Credits/AI Generation/Content's notes above). If the publish raises, `app/tasks.py` never commits the "fired" state change; the occurrence stays `status=scheduled` and gets retried on the next scan once the lock expires. Losing this specific event would mean a post silently never reaches Social Publishing, which is worse than a delayed retry.
- **Content ownership cache, not a live check**: `POST /scheduled` validates `content_id` against a local `available_content` table populated by consuming `content.created`, rather than calling the Content Service directly — matches the spec's framing that Scheduler "knows what is available to schedule" from that event, and avoids a cross-service call on every schedule request. It does mean a content item briefly won't be schedulable if Scheduler's consumer hasn't processed its `content.created` event yet (normally sub-second).
- **No cross-service content details on the calendar view**: `GET /scheduled` returns `content_id`, not the post's title/body — fetching that is left to the frontend calling Content directly, rather than Scheduler doing an N+1 fan-out of cross-service calls per calendar render. The frontend didn't actually do that lookup until Slice 15, though — the calendar showed a scheduled time with no indication of what was scheduled for a long stretch of this project's life, fixed with a client-side join against content it was already fetching for a different dropdown (see Slice 15's "Calendar now shows what was actually scheduled").
- **Only `approved` content can actually be scheduled, as of Slice 14**: the `available_content` cache only ever tracked *existence*, not status, so a still-`draft` piece of content was just as schedulable as an approved one. Scheduler now also consumes `content.updated` (not just `content.created`) to keep a cached status column in sync with Content's real `draft → approved → published` machine; `POST /scheduled` rejects anything not currently `approved` with a real `409`, and the Calendar's content picker only lists approved items.
- **A real cross-invocation asyncpg bug meant no scheduled post had ever fired past the very first Celery task run**: the async SQLAlchemy engine is created once at module import, but the Celery task wraps its body in `asyncio.run()`, which opens a *brand-new* event loop on every single invocation — asyncpg connections are bound to the loop that created them, so a pooled connection from one invocation was invalid on the next. This crashed with "attached to a different loop" on the task's second-ever run, and "another operation is in progress" on every run after that, meaning this had been silently broken since the service first started. Fixed by disposing the engine at the end of each run (inside the same loop, before it dies), so the next `asyncio.run()` opens fresh, correctly-loop-bound connections. Verified live: a real overdue scheduled post fired and published to LinkedIn immediately after this fix deployed.

### Social Publishing Service notes

- **LinkedIn credentials are placeholders** (`linkedin-client-id/secret-placeholder`) — per the spec, every developer registers their own LinkedIn Developer App for local testing (LinkedIn issues API access per app, not shared across a team), enabling the "Sign In with LinkedIn using OpenID Connect" and "Share on LinkedIn" products with scopes `openid profile email w_member_social`. `LINKEDIN_REDIRECT_URI` must exactly match a redirect URL registered on that app.
- **The OAuth callback is genuinely public, by necessity**: LinkedIn's browser redirect back to `/social/linkedin/callback` can't carry an `Authorization` header, so unlike almost every other route in this platform, the Gateway proxies it unauthenticated. The caller's identity instead travels in a signed `state` param — `POST /social/linkedin/connect` (a normal protected route) creates it via a dedicated Fernet key (`OAUTH_STATE_KEY`, separate from the key used to encrypt stored tokens) with a 10-minute TTL baked into the Fernet token itself, and the callback verifies+decrypts it to recover `account_id`/`user_id` with no database lookup needed.
- **Tokens are encrypted at rest** (Fernet, `TOKEN_ENCRYPTION_KEY`) — `social_connections.access_token_encrypted`/`refresh_token_encrypted` are never stored in plaintext; they're only decrypted in memory for the duration of an outbound LinkedIn API call (`app/crypto.py`).
- **Image publishing (bonus)**: when `content.scheduled` resolves to a post with an `image_url`, the consumer registers an upload via LinkedIn's Assets API, downloads the image bytes (from Content's `/uploads/*` or a Pollinations.ai URL — either works, it's just an HTTP GET), `PUT`s them to LinkedIn's returned upload URL, and references the resulting asset URN in the UGC post payload — producing a text+image post instead of text-only, exactly as the bonus feature describes.
- **Retry semantics split on failure type**: a transient LinkedIn failure (rate limit, 5xx, network error) re-raises out of the consumer, which lets `py_shared.rabbitmq`'s existing bounded-retry-then-DLX mechanism handle it (no separate custom backoff timer — the platform-wide mechanism already covers "retry with backoff... route to DLQ after max attempts"). A permanent failure (no LinkedIn connection, content deleted) is caught locally, recorded, and emits `post.failed` immediately without retrying — retrying something that will fail identically every time would just waste the bounded-retry budget.
- **Token refresh is honest about a real LinkedIn constraint**: `app/token_refresh.py` runs hourly and refreshes any connection with a stored `refresh_token`, but LinkedIn's default 3-legged OAuth token doesn't grant refresh tokens unless your specific Developer App has been approved for that capability — most test/local apps won't have it. Connections without a `refresh_token` just log a warning near expiry rather than erroring; the user will need to reconnect once the (typically ~60-day) access token actually expires.
- **Cross-service content fetch, not an event payload**: `content.scheduled`'s payload only carries `content_id` (not the post text), so the consumer calls Content's `GET /content/{id}` directly (service-to-service, bypassing the Gateway) rather than requiring Content to duplicate its own data into every event — same pattern as Credits calling Billing.
- **Publish jobs now atomically claim themselves before calling LinkedIn**: a crash between a successful LinkedIn post and marking the `publish_jobs` row `published` would have let redelivery of the same `content.scheduled` event re-run the whole handler and create a **second real LinkedIn post** — found during the Slice 14 spec-compliance audit. The consumer now atomically claims the job (a conditional `UPDATE ... WHERE status='pending'`) before ever calling LinkedIn's API, closing the specific duplication window; this doesn't eliminate every conceivable timing gap around an external, non-idempotent side effect (see Slice 13's "gaps deliberately not fixed" section below for the one that remains), but it closes the one that was actually open.
- **`content.updated`/`post.published` now carry `content_id` forward** so Content itself can detect a real LinkedIn publish and flip its own status accordingly (see Content Service notes above) — this event's payload previously stopped at the Social Publishing side of the flow.

### Scraper Service notes

- **The first (and only) MongoDB-backed service**: per the spec's data-ownership table, Scraper owns no Postgres schema at all — `scrape_jobs`, `scraped_documents`, and even its own `processed_events` idempotency collection all live in MongoDB (`app/mongo.py`, via Motor's async driver). The `py_shared.rabbitmq.consume()` idempotency hooks are plain async callables, so backing them with Mongo instead of Postgres required zero changes to the shared library — proof the abstraction was right.
- **Playwright over Crawl4AI**: the spec allows either; Playwright was simpler for this scope's "load the page, grab title/text/html" need with no extra wrapper. The Dockerfile deliberately uses Microsoft's official `mcr.microsoft.com/playwright/python` base image (browsers + OS deps pre-installed) instead of `playwright install` on a bare `python:3.11-slim`, which reliably fails without a list of extra apt packages that image already has.
- **robots.txt compliance is real, not decorative**: `app/robots.py` fetches `robots.txt` itself via httpx (async) and hands the raw lines to `urllib.robotparser.RobotFileParser.parse()`, avoiding that library's own blocking `urlopen` call — `crawl()` in `app/crawler.py` refuses to proceed if disallowed, and treats that as a **permanent** failure (no retry — robots.txt won't change its mind on redelivery), distinct from a transient crawl error which does retry via the standard bounded-retry-then-DLX path.
- **Per-domain rate limiting is in-process, not distributed**: `app/rate_limiter.py` tracks the last request time per hostname in a plain dict guarded by an `asyncio.Lock`, sufficient for the single-worker deployment this scope assumes — scaling to multiple scraper worker replicas later would need this moved to a shared store (Redis) to stay accurate across them, which isn't done here.
- **Recurring jobs use a genuinely different mechanism than Scheduler**: the spec calls for "an internal scheduler" here, as opposed to the dedicated Scheduler Service's Celery Beat setup — so `app/recurring.py` is a plain asyncio loop inside this one service (started in `main.py`'s lifespan, no extra containers), scanning for `scrape_jobs` documents whose `next_run_at` has passed. Each firing inserts a fresh one-off (`recurrence: "none"`) job document for that occurrence and advances the parent's `next_run_at`, mirroring the pattern Scheduler uses but self-contained.
- **A real version mismatch meant no crawl had ever actually succeeded**: `requirements.txt` pinned `playwright>=1.45.0` (open-ended), but the Dockerfile's base image (`mcr.microsoft.com/playwright/python:v1.45.0-jammy`) only has Chromium pre-installed for exactly that version — `pip` always resolved a newer `playwright` package expecting a newer, not-installed browser revision, so every single crawl failed with `BrowserType.launch: Executable doesn't exist at .../chromium_headless_shell-.../`. Pinned exactly to `playwright==1.45.0`; verified with a live crawl against a real URL.
- **`GET /scrape-jobs/{job_id}/document`** resolves the most recently-created `ScrapedDocument` for a job — added because the job document itself never stored a back-reference to its resulting document, which the frontend needs to jump straight from a completed job to its result without the caller tracking `document_id` separately.
- **The standalone frontend UI (`ScraperJobs.tsx`, added in Slice 14) was removed again in Slice 15** once Content Studio's auto-research toggle made the same underlying capability reachable without a separate page (see Slice 15's "Content Studio: optional automatic web research" for why). The REST API this page drove (`/scrape-jobs`, the async job+recurrence flow, everything else described above) is untouched and still fully functional — only the page and its nav link are gone, not the feature or the service.
- **`app/search.py` and `POST /internal/research` (Slice 15)**: a separate, synchronous capability alongside the async job flow above — given just a topic (no URL), finds and fetches factual context via Wikipedia's API rather than a general web search (see Slice 15 for why: DuckDuckGo's free option CAPTCHA-challenges scripted requests, confirmed directly). Used by AI Generation's research toggle; service-to-service only, same `/internal/*` protection as everything else.

### Notification Service notes

- **Retroactive fixes this slice needed to make elsewhere work**: most consumed events only carry an `account_id` or `user_id`, not an email — and a couple of email flows the spec explicitly calls for (working verification links, team-invite emails) were never actually wired end-to-end because Notification didn't exist yet when Auth and User/Tenant shipped. Three small additions, all backward-compatible:
  - Auth's `user.registered` event now includes `verification_token` (previously only returned in the dev-only `dev_verification_token` API response field) — Notification builds the real `/verify-email?token=...` link from it.
  - User/Tenant's `POST /accounts/{id}/invite` now actually publishes an `invite.created` event (`{invite_id, account_id, email, token, role}`) — previously it created the `Invite` row and returned a dev token but published nothing at all, so nothing could ever have emailed the invitee even once Notification existed.
  - Two new **internal-only** endpoints: Auth's `GET /internal/users/{user_id}` (resolve email from user_id) and User/Tenant's `GET /internal/accounts/{account_id}/owner` (resolve the owner's user_id from account_id) — chained together (`app/identity_resolver.py`) to turn an `account_id`-only event into a recipient email.
- **Real security gap found and fixed while wiring this up**: the Gateway's catch-all proxy routes (`/auth/{path:path}` etc.) matched on path prefix alone, so a public request to `/auth/internal/users/{id}` would have been happily forwarded straight through to Auth's new unauthenticated internal endpoint — trivially leaking any user's email to anyone on the internet. Fixed with `_reject_internal_paths()` in the Gateway's `app/api/routes.py`, applied to every proxy route (both the shared `_proxy_protected` helper and the standalone `/auth/*` proxy), rejecting any path segment starting with `internal` before it ever reaches `forward()`. Verified directly: `GET /auth/internal/users/<uuid>` now returns `404` from the Gateway itself, never reaching Auth.
- **Four separate exchange bindings, one shared idempotency table**: `app/events.py` declares four independent queues (one per exchange: `user_events`, `domain_events`, `billing_events`, `social_events`), each with its own routing keys and DLX, but all four route through the same `processed_events` table for idempotency — safe because `event_id` is a UUID, globally unique regardless of which exchange it arrived on.
- **Email failures are swallowed, not retried**: unlike most consumers in this codebase, `app/notify.py`'s `send_and_log()` never re-raises on a send failure — it logs the failure to `notification_log` (status=`failed`) and returns normally. Emails are treated as inherently best-effort here (there's no real harm in occasionally missing one, unlike e.g. Scheduler's `content.scheduled`), so retrying via the bounded-retry-then-DLX mechanism wasn't judged worth the added complexity for this scope.
- **Email delivery switched from Resend to plain SMTP in Slice 15** (see that section below for the full reasoning) — `app/email_client.py` is now `aiosmtplib`-backed, configured via `SMTP_HOST`/`PORT`/`USERNAME`/`PASSWORD`/`FROM_EMAIL`, with placeholders by default (`smtp-placeholder@gmail.com`) until real credentials are set. Slack alerts just log a warning instead of posting when no webhook URL is configured, so ops alerts are still visible somewhere even unconfigured.
- **Every dev-only token leak the spec explicitly warns against has now been closed**: the forgot-password OTP, the signup verification token, and the team-invite token were all, at different points, returned directly in their respective API responses (and rendered as one-click bypass buttons in the frontend) as a development convenience predating this service's existence. Now that Notification genuinely sends all three by real email, every one of those response fields has been removed — the frontend shows a plain "check your email" confirmation instead, and none of these flows can be completed anymore without actually receiving the email.
- **`send_and_log()` now checks its own log before resending**: found during the Slice 14 spec-compliance audit — a redelivered event in the exact "crash after send, before log" window (the deliberately-unfixed gap Slice 13 already documented, see below) could still fire a real duplicate email. A pre-send existence check against `notification_log` for the same `event_id` closes the common case without pretending the underlying non-idempotent side effect (an external email send) is now perfectly exactly-once.

### Admin/Ops Service notes

- **A genuinely new, platform-level concept had to be introduced**: every other service's JWT `role` claim (`owner`/`admin`/`member`) is account-scoped, but the spec calls for "a SuperAdmin role, platform-level, not account-scoped." That required touching the shared library every service depends on: `py_shared/jwt.py`'s `TokenClaims`/`issue_access_token()` gained an `is_superadmin` field (defaulting `False`, so every existing call site kept working unchanged); Auth's `User` model gained an `is_platform_admin` column (an operator-only flag — no signup flow sets it, flip it directly in the DB for whoever operates this platform); the Gateway's `Identity` and its `_proxy_protected()` helper now read and forward it as `X-Is-Superadmin`. `TenantAdmin` (the spec's other role, restricted to one's own account) maps onto the existing account-scoped `owner`/`admin` roles rather than inventing a third role system — see `require_access_to_account()` in `app/identity.py`.
- **Four small `/internal/*` endpoints added elsewhere, purely to support this service**: User/Tenant's `GET /internal/accounts` (cross-account directory) and `GET /internal/accounts/{id}/summary` (name/type/plan_tier/member_count), Billing's `GET /internal/accounts/{id}/subscription`, Credits' `GET /internal/accounts/{id}/balance`, and Usage's `GET /internal/accounts/{id}/summary` — each mirrors an existing identity-scoped endpoint but takes an explicit `account_id` instead of trusting the caller's own identity, since Admin needs to read *any* account's data, not just its own. All four are unreachable from the public internet via the same `_reject_internal_paths()` mechanism Notification's slice introduced.
- **Session listing has no secondary index**: Auth's `jti:*` Redis keys were enriched (`{"user_id":..., "account_id":...}` JSON instead of a bare user_id string) so `GET /admin/accounts/{id}/sessions` can filter by account, but there's no reverse index from account_id → jti — listing does a full `SCAN jti:*` and filters client-side. Fine at this scope's session volume; a real secondary index (or moving this to a proper session store) would matter at much larger scale.
- **The audit consumer has no way to discover exchanges dynamically**: `AUDITED_EXCHANGES` in `app/events.py` is a hardcoded list of every topic exchange that exists across the platform today (`user_events`, `domain_events`, `billing_events`, `social_events`, `scraper_events`, `ai_events`, `webhook_events`) — RabbitMQ's client API has no "list exchanges" call without broker management permissions this service intentionally doesn't have, so a future slice that introduces a new exchange needs a one-line addition here or its events silently won't reach the audit log.
- **One shared idempotency table across seven queues**: like Notification, all seven exchange-bound queues route through the same `processed_events` table — safe because every event's `event_id` is a UUID, globally unique regardless of which exchange or queue delivered it.
- **Revenue and owner-profile visibility (Slice 14, beyond the spec's own aggregation requirements)**: the account directory and per-account overview now also show real revenue — `total_revenue_cents`, sourced from a new Billing `GET /internal/revenue` (one grouped query summing paid invoices per account, not one call per account) — and the account owner's email, verification status, and signup date, resolved by chaining User/Tenant's existing owner-lookup endpoint into a small extension of Auth's existing `GET /internal/users/{id}` (which already returned `email`; `email_verified`/`created_at` were added to the same response). Both are natural extensions of the same read-only internal-endpoint pattern every other admin aggregation already used, not new architecture.
- **Provisioning a SuperAdmin has no dedicated flow, by design**: per the spec, `is_platform_admin` is an operator-only flag with no signup path of its own — the only way to create one is a real signup followed by an operator flipping `email_verified=true, is_platform_admin=true` directly in `auth.users`. There is deliberately no admin-signup endpoint or admin-invite flow to audit here; the absence is the correct implementation, not a missing feature.
- **A dedicated SuperAdmin experience, and a platform-wide user directory (Slice 15)**: the frontend nav/header no longer treats a SuperAdmin like a regular tenant account (see Slice 15's "SuperAdmin: a dedicated UI, and undeletable" for the full reasoning), and a new `GET /admin/users` gives a flat, account-agnostic list of every user plus total platform revenue — deliberately separate from the existing account-centric directory above, not a replacement for it. The same section also covers why `DELETE /account` now refuses to delete a SuperAdmin account at all, found the hard way after this project's own SuperAdmin account got deleted through the ordinary self-service flow mid-session.

Every FastAPI service shares `libs/py-shared`:
- `jwt.py` — RS256 issue/decode helpers (Auth Service holds the private key; Gateway only needs the public key)
- `rabbitmq.py` — durable topic-exchange publish with publisher confirms, and a consume() helper that enforces idempotent processing (via each service's own `processed_events` table) and bounded-retry-then-DLX delivery
- `errors.py` — the `{error: {code, message, details}}` response schema used by every service

The Gateway verifies the JWT once and forwards trusted `X-User-Id` / `X-Account-Id` / `X-Role` headers to downstream services, so internal services don't duplicate JWT verification.

**Fixed since Slice 1** (right before the frontend fill-in pass, since nearly every account-scoped page would have broken against it): `POST /auth/login` originally issued a JWT with `account_id` set to a placeholder (the user's own id acting as their individual account scope), because Auth and User/Tenant didn't coordinate to look up the user's *real* account id at login time. Auth now calls a new User/Tenant internal endpoint (`GET /internal/users/{user_id}/accounts`) to resolve the real default account (the first one returned, which is the user's individual account on their first-ever login) — falling back to the old placeholder only in the rare case User/Tenant hasn't yet consumed `user.registered` (a sub-second race right after signup). `POST /auth/switch-account` (new) validates membership in a target account via the same lookup and issues a freshly-scoped token, backing the frontend's Account Switcher exactly as the spec describes ("Account Switcher... triggers a new account-scoped JWT"). `POST /auth/refresh` also gained an optional `account_id` field so silent refresh (every ~15 minutes, since that's the access token TTL) doesn't reset a switched-away-from-default account back to the default.

**Login didn't actually enforce email verification until Slice 15**: `POST /auth/login` checked credentials but never `email_verified` — any account could log in immediately after signup regardless of whether the verification link had ever been clicked, going unnoticed largely because Resend's sandbox mode limited real delivery to one address anyway. Now checked (after password verification, so a wrong-password guess and a real-but-unverified account get the identical `invalid_credentials`-shaped non-answer either way) — see Slice 15's "Login now actually enforces email verification" for the fix and the account cleanup it required.

## Local setup

Postgres is a **containerized service** (`postgres` in `docker-compose.yml`), same as Redis, RabbitMQ, and MongoDB — the whole stack is self-contained behind a single `docker-compose up`, no host-level database install required.

1. Copy `.env.example` to `.env`. Generate a dev RS256 keypair and paste the PEM contents in (see the comment in `.env.example` for the exact `openssl` commands), or reuse the one already generated for this session.
2. `docker-compose up --build`

**Postgres data model, unchanged from when it ran natively**: one shared instance, one schema per service (`auth`, `usertenant`, `billing`, etc.), each created automatically by that service's own `init_db()` on first boot — no manual role/database creation needed anymore. The `postgres` service doesn't publish a host port by default (only other containers reach it, over the internal Docker network as `postgres:5432`); add a `ports:` mapping in `docker-compose.yml` if you want `psql` access directly from the host.

**This ran natively on the host earlier in this project** (PostgreSQL 18 installed directly on Windows, reached via `host.docker.internal`, with an added `pg_hba.conf` rule for Docker's internal network range) — a deliberate choice at the time for an environment that already had Postgres installed, not a spec requirement. It was switched to a containerized `postgres` service later specifically because relying on a host-level install is a real deployment blocker the moment this stack needs to run on a different machine: `host.docker.internal` doesn't resolve on native Linux Docker without an explicit `extra_hosts` entry (most real servers), the database would need reinstalling and reconfiguring by hand on every new host, and there was no backup story for data living outside Docker's own volume management. Migrating meant taking a real `pg_dump` of the live database (accounts, real Stripe test invoices, the SuperAdmin account, everything) and restoring it into the new containerized instance rather than starting from empty — verified live via matching row counts and a real login against an existing account before and after the switch.

**This has now actually been run, end-to-end, on a real machine** — not just statically verified. All 20 containers (13 backend services + Gateway + frontend + Postgres/Redis/RabbitMQ/MongoDB + the Scheduler's worker/beat pair) come up and stay up; every service's `/healthz` returns `200`; a real signup through the Gateway creates rows in Postgres and — via a real RabbitMQ round-trip — an individual account and owner membership in the User/Tenant service, confirmed by querying Postgres directly afterward. ### Bugs found via live testing (already fixed)

Everything up to this point in the document had only been statically verified (imports, `py_compile`, `TestClient` hits with no real infrastructure behind them) — the following three only surfaced once the full stack actually ran together, which is exactly the gap a live test is supposed to close:

1. **Scraper's Dockerfile pinned an incompatible Python version.** It's built on Playwright's official image (`mcr.microsoft.com/playwright/python:v1.45.0-jammy`), which ships Python 3.10 — but `libs/py-shared`'s `pyproject.toml` declared `requires-python = ">=3.11"` with no actual technical basis (nothing in the shared library uses 3.11-only syntax; every file already has `from __future__ import annotations`). Lowered to `>=3.10`.
2. **Scraper's own code used `datetime.UTC`**, a constant that doesn't exist before Python 3.11 — a second, deeper layer of the same version mismatch, invisible to every previous check in this repo because those all ran against a local Python 3.14 interpreter, never the actual Playwright base image. Fixed by switching to the version-portable `datetime.timezone.utc` in Scraper's three affected files (`app/api/routes.py`, `app/events.py`, `app/recurring.py`) — every other service stays on `datetime.UTC` since they run on `python:3.11-slim` and have no such constraint.
3. **Every RabbitMQ consumer had a silent, unrecoverable startup race.** `libs/py-shared/py_shared/rabbitmq.py`'s `get_connection()` had no retry logic on the *first* connection attempt — and on a real `docker-compose up --build` cold start, nearly every one of the 13 consumer-declaring services hit "Connection refused" at least once, because Docker's healthcheck can report RabbitMQ "healthy" before its AMQP listener actually accepts connections. Since every service starts its consumer via a bare `asyncio.create_task(...)` with no supervisor above it, that first failure killed the consumer forever — HTTP endpoints kept responding normally the whole time, so nothing *looked* broken; events just silently stopped being processed. Fixed with exponential-backoff retry (10 attempts, 1s→30s) in the one shared `get_connection()` function every service's consumer goes through, rather than patching each service individually. Verified after the fix: a genuine cold `docker-compose down && docker-compose up --build -d` now brings up all 20 real RabbitMQ queues with exactly one active consumer each and zero stuck messages, confirmed via the RabbitMQ management API — not just "the container says Up."
4. **(Found later, migrating Postgres from a native host install into a container)** The official `postgres:18-alpine` image changed its expected volume layout: 18+ images store data in a major-version-specific subdirectory (`pg_ctlcluster`-style) and expect the volume mounted one level up, at `/var/lib/postgresql` — mounting a volume directly at `/var/lib/postgresql/data` (the correct convention for every Postgres image before 18) makes the entrypoint detect a stray "unused mount" and refuse to start at all. Fixed by mounting `postgres_data` at `/var/lib/postgresql` instead. Caught immediately since the container reported itself `unhealthy` rather than silently misbehaving — the healthcheck doing exactly its job.

## Slice 13: Reliability hardening pass

The Definition of Done requires every service to survive a forced consumer restart with no data loss or duplication. Each slice's own verification steps spot-checked this per-service as it was built, but this pass went through every event consumer in the platform specifically looking for the one gap that pattern doesn't automatically close (see below), rather than re-verifying things already covered (DLX/retry, publisher confirms, durable delivery — all structurally enforced by `py_shared.rabbitmq` itself and unchanged here).

### What "restart-safe" actually requires, and where it was missing

`py_shared.rabbitmq.consume()` runs `handler(payload)`, and only *after* it returns successfully does it call `mark_processed(event_id)`; only after *that* does it ack the message back to the broker. That ordering means the shared `processed_events` idempotency check reliably catches redelivery *after* both of those have committed — but a crash landing *between* the handler's own commit and the `mark_processed` commit (exactly what "kill the container mid-burst" probes) leaves `is_processed()` still `False`, so redelivery re-runs the handler's business logic in full. The processed_events table is necessary but not sufficient — **every handler needs its own idempotency check against its own schema**, and auditing for that specifically turned up four real duplication bugs and one related false-failure bug that had gone unnoticed because nothing had actually forced this exact crash timing yet:

- **User/Tenant's `user.registered` handler** created an individual Account + owner membership with no check for one already existing — redelivery in that crash window would have given one user two individual accounts. Fixed: skip if the user already has *any* account membership (a brand-new user has zero, so this is a reliable signal).
- **Credits' `invoice.paid` handler** appended a `purchase_grant` ledger row with no check — redelivery would double-credit the account. **`refund.issued`** had the same gap for `refund_clawback` rows. Both fixed with an existence check keyed on `(reference_id, reason)`. (`marketplace.payment_completed` was already correct — it was built checking listing status from the start.)
- **Usage's `ai.generation_completed` handler** inserted a `usage_ledger` row with no check — redelivery would permanently double-count that call's cost/tokens (Redis alone would self-heal via the reconciliation loop; the durable Postgres row would not). Fixed with a check keyed on `generation_job_id`.
- **Billing's Stripe webhook handler** actually had the right idempotency signal already sitting right there — inserting the `SubscriptionEvent` audit row happens in the *same transaction* as every `_apply_*` side effect and its outbox-event insert, so "a SubscriptionEvent row for this stripe_event_id already exists" is a fully valid, atomic guard. The bug was that the code checked for it but never `return`ed early, so `_apply_payment_failed`/`_apply_subscription_updated`/`_apply_checkout_session_completed` ran again on redelivery regardless — re-extending a dunning grace period and double-emitting `payment.failed`/`subscription.updated`/`marketplace.payment_completed` outbox events every time. Fixed by returning immediately when the row already exists.
- **Scraper's `scrape.requested` handler** — `scraped_documents` and the `scrape_jobs` status update are two separate MongoDB writes (no multi-document transaction wraps them), so a crash between them left the job at `status=pending`; without a check, redelivery re-crawled and inserted a *second* document. Fixed: if a document already exists for that `scrape_job_id`, just finish the status update instead of re-crawling.
- **Admin's audit-log handler** was a different failure mode entirely: `AuditLog.event_id` already has a unique DB constraint, so redelivery in that same crash window wouldn't have silently duplicated the row — it would have hit an `IntegrityError`, which the outer `consume()` loop treats as a genuine handler failure and retries pointlessly until the (already-correctly-recorded) event lands in the DLQ as a false failure. Fixed with the same existence-check pattern, avoiding the wasted retries.
- **`py_shared/rabbitmq.py`'s `consume()` docstring** now spells out this exact nuance directly, so the next new consumer gets built with it in mind instead of this pass needing to be repeated by hand.

Everything above was found and fixed by code review, then confirmed by re-importing every touched service's app with its real dependencies (catching, among other things, a missing `select` import in the User/Tenant fix that would otherwise have been a `NameError` at the exact moment the fix was needed) — not by an actual `docker-compose` forced-restart run, since Docker isn't available in this environment. The verification steps below describe exactly that run for whoever has Docker to do it.

### Two gaps found but deliberately *not* "fixed"

Two consumers have a structurally different problem this pass's fix pattern can't close, and no attempt was made to half-fix them with something that wouldn't actually be correct:

- **Social Publishing's `content.scheduled` handler** calls LinkedIn's UGC Posts API *before* marking the `publish_jobs` row `published`. A crash in that exact window — after LinkedIn successfully creates the post, before the DB commit — means redelivery re-runs the whole handler and creates a **second real LinkedIn post**. This is an external, non-idempotent side effect, not an internal DB write; closing it properly needs either a client-supplied idempotency key LinkedIn's API would need to support (not something this integration currently sends) or a "posting-in-progress" pre-commit plus a reconciliation check against LinkedIn's own post history, which is real scope beyond this pass. (Slice 14 later added an atomic pre-claim of the job row before calling LinkedIn at all, which closes the ordinary redelivery-after-processed-events-check window this section describes — but the fundamental gap for a crash landing *during* the LinkedIn call itself, with no idempotency key on LinkedIn's side, is unchanged and still real.)
- **Notification's `send_and_log()`** sends the email *before* logging it, for the same reason: there's no dedup key to check before an email send, and marking "about to send" before calling the provider still doesn't prevent redelivery mid-flight from sending twice. A user could get one duplicate email in this exact crash window. (Slice 14 added a pre-send check against `notification_log` for the same `event_id`, which closes the common redelivery case — but a crash landing *between* a successful send and that log write, same as the point above, is structurally the same unclosed gap in miniature.)

Both are documented here rather than silently left alongside the fixed ones, since "found and consciously deferred with a stated reason" is a materially different, more honest status than "not found" — and staying honest about what a later partial mitigation does and doesn't close is the same principle applied a second time.

### Verifying Slice 13 end-to-end

For each of the six fixed handlers above, on a machine with Docker: manually publish (or trigger via the normal flow) the relevant event, kill `-9` the consuming service's container after its handler's own commit would plausibly have happened but before the next scan/poll interval, restart it, and confirm via the relevant table (`account_members`, `credits_ledger`, `usage_ledger`, `subscription_events`+`outbox_events`, `scraped_documents`, `audit_log`) that no duplicate row exists and the event's effects landed exactly once. For the two acknowledged gaps, the honest verification is confirming the failure mode reproduces under that exact timing (a duplicate LinkedIn post / a duplicate email) — not that it's absent, since it isn't fully closed.

## Slice 14: Post-launch audits, billing/refund completion, and production deployment

Slice 13 closed the one *structural* restart-safety gap the reliability pass targeted, but didn't re-check the platform against the original spec line by line. This slice covers two further spec-compliance audits (run in direct response to real bug reports and a challenge that a prior pass had missed things — it had), the billing/refund functionality those audits and live usage surfaced as broken, feature completion the frontend fill-in had left out, and finally putting the whole stack behind a single public HTTPS entry point. Most individual fixes are documented in-depth in their owning service's notes section above (linked inline below); this section is the consolidated list plus everything that doesn't belong to one single service.

### Spec-compliance audit #1 — eight gaps

Run after the reliability pass, against the original spec text rather than against "does it structurally survive a restart":

1. Credits never actually debited the ledger on `ai.generation_completed` — it only tracked Usage's token quota, so the credit balance shown was disconnected from what generations actually cost (see Credits notes above).
2. Two duplicate-side-effect races: Social Publishing didn't atomically claim a publish job before calling LinkedIn, and Notification didn't check its own log before resending an email (see Social Publishing / Notification notes above).
3. Scraper's `scrape.completed` was never wired into Content as a real draft, despite Content already having the exact `ai.generation_completed` → draft pattern to copy.
4. The forgot-password OTP was leaked directly in the API response instead of actually being emailed — fixed by routing it through Notification for real, once Notification could actually send it.
5. JWT storage didn't match the spec's target: the access token now lives only in memory (React state, never `localStorage`), and the refresh token moved into an `httpOnly` cookie set directly by the Gateway — neither is readable by page JavaScript, closing an XSS-driven token-theft surface a `localStorage`-based scheme would have left open.
6. The Gateway had no role enforcement at all in front of Billing/Credits — any authenticated member (not just an owner/admin) could hit endpoints meant to be owner-gated. Added the same server-side role check pattern already used elsewhere.
7. Several handlers were stubbed or missing entirely: User/Tenant's `account.updated`/`invoice.paid`/`subscription.downgraded` consumption, Billing's dunning scanner (see Billing notes above), a dedicated `usage_events` exchange, a Gateway dashboard-aggregation endpoint, a real Redis token-bucket rate limiter (replacing a simpler placeholder), and a couple of frontend pricing/calendar-week-view gaps.
8. No CI at all — added a GitHub Actions workflow running a frontend production build, a Python syntax check across every service, and a Docker build, gating merges into `dev`.

### Spec-compliance audit #2 — five more gaps, plus a follow-up token-leak sweep

Run again after the first pass, specifically because a direct challenge that gaps had still been missed turned out to be correct:

1. **Retry backoff**: `py_shared.rabbitmq`'s consumer retried a failed message immediately and at an unbounded rate — added exponential backoff (`RETRY_BACKOFF_BASE_SECONDS=2.0` doubling up to `RETRY_BACKOFF_MAX_SECONDS=60.0`) before each republish, since nothing in this codebase sets per-consumer prefetch/QoS to otherwise throttle a hot retry loop.
2. **A full Scraper frontend** — job creation, status polling, and a result viewer — plus the new `GET /scrape-jobs/{job_id}/document` endpoint it needed (see Scraper notes above).
3. **A content version-history viewer**, finally giving the backend's `GET /content/{id}/versions` (live since Slice 6) an actual UI (see Content notes above).
4. **A refund-request flow** on the Billing & Invoices page — this is what then led directly into the full 7-day/95% refund policy work below once it was actually exercised against a real Stripe account.
5. **The Gateway's `GET /dashboard/summary` aggregation endpoint** (added in audit #1's item 7) had no frontend caller at all — `Dashboard.tsx` was still making four separate calls it aggregated client-side. Wired the frontend to the existing endpoint instead of leaving it dead code, and surfaced plan tier/team size in the app header while at it.

The same "audit under direct challenge" pass also caught a **second instance of the OTP leak class of bug**: `POST /signup` still returned `dev_verification_token` (with `SignUp.tsx` rendering a one-click bypass button from it) and `POST /accounts/{id}/invite` still returned `dev_invite_token` — both predating Notification's real email sends and never removed once Notification made them unnecessary and actively harmful (either bypass skips the actual point of email verification / invite-to-a-specific-person). Both fields were removed from their response schemas; the frontend now shows a "check your email"/"invite sent" confirmation instead.

### Billing, refunds, and plan-switch correctness

Chasing real bugs against a live Stripe test-mode account (rather than static review) surfaced a chain of issues, each documented in depth in the Billing notes above: the **transactional outbox envelope bug** (the single most impactful fix this session — it silently broke cross-service sync for nearly every billing-driven feature since Billing was first built), **Stripe's Basil API version** breaking both payment-intent resolution and multi-line proration-invoice plan detection, **immediate-charge plan switching**, the **7-day/95% refund policy** with **auto-cancel-and-downgrade-to-Free on refund**, and the **real `refunded_amount_cents` field** replacing a frontend-only, per-session refund-status guess. Two smaller but equally real bugs were fixed along the way: `credits_ledger.reference_id` was `VARCHAR(64)`, too short for a real Stripe checkout session id, failing every "buy extra credits" purchase outright; and `auth.User`'s ORM relationship to `Credential` was missing `passive_deletes=True`, so SQLAlchemy tried to null out a `NOT NULL` foreign key itself instead of letting Postgres's own `ON DELETE CASCADE` handle it — crashing every real `DELETE /account` call.

### Session handling and team-invite correctness

- **A concurrent token-refresh race could bounce a genuinely-logged-in user back to the login page**: `refreshAccessToken()` in `frontend/src/api/client.ts` had no protection against being called more than once at a time, but real scenarios trigger several concurrent calls routinely — React StrictMode double-invokes `AuthProvider`'s mount effect in development, and a page like the Billing dashboard fires several authenticated requests at once on mount, any of which can independently trigger its own refresh on a `401`. Since Auth's `POST /auth/refresh` does genuine single-use rotation (revoking the old refresh token in the same transaction that issues a new pair), concurrent calls reading the same not-yet-rotated cookie is a real race, confirmed directly: two truly concurrent refresh calls could **both** succeed with mismatched token lineages — an even less safe outcome than a clean win/lose race. This reliably surfaced after a real Stripe Checkout, since the access token has genuinely expired by the multi-minute time it takes to complete checkout, and landing back on the Billing page fires several authenticated calls at once. Fixed by sharing one in-flight refresh promise across every concurrent caller, so only one real `/refresh` request is ever in flight at a time.
- **`accept_invite` never verified the invite was actually being accepted by its intended recipient**: whichever `user_id` happened to be authenticated when an invite link was clicked got added to the account, regardless of whether it matched the invite's target email — in the specific case that surfaced this, the *inviter* stayed logged in, clicked their own invite link out of habit, and crashed with a raw database error trying to double-join an account they already owned, instead of getting any meaningful response. Fixed by resolving the accepting identity's real email via a new cross-service call to Auth's `GET /internal/users/{id}` (User/Tenant owns membership but not identity) and rejecting with a clear `403` if it doesn't match the invite's target email — this is what actually makes an invite "for a specific person" rather than a bearer token anyone holding the link could redeem as themselves. The same fix closed a genuine TOCTOU race: checking `invite.status == "pending"` and then inserting the membership row weren't atomic, so two concurrent accept attempts on the same token could both pass the check before either committed. Replaced with a conditional `UPDATE ... WHERE status='pending'` and a rowcount check — the same atomic-claim shape Social Publishing's scheduled-post handler already used.

### Frontend feature completion

Beyond the audit-driven fixes already covered above, the frontend gained a full pass of features the original fill-in (Slice 12) either stubbed or left out entirely:

- **A one-time 50-credit signup bonus** and **plan-gated features**: Team Management (invite members) requires the Team plan (enforced in User/Tenant, which already caches `plan_tier`); LinkedIn Connections, Calendar/Scheduler, and Marketplace require Pro or Team, enforced at the Gateway via a `plan_access` module that caches Billing's subscription lookup in Redis (30s TTL) instead of a live call per request. The frontend nav/routes hide or block these for Free-plan accounts via a new `AccountContext` + `PlanGateRoute`, following the same UX-only-not-a-security-boundary pattern `OwnerRoute`/`SuperAdminRoute` already established.
- **Real profile and account management**: Auth gained a `name` field on `User`, `GET`/`PATCH /auth/profile`, and a genuinely irreversible `DELETE /auth/account` (requires re-entering the password as the actual safety gate — a frontend type-to-confirm dialog is a UX speed bump, not a security control on its own) that cascades Auth's own tables and publishes `user.deleted` for User/Tenant to clean up memberships across every account the user belonged to.
- **Full light/dark theme support** (Tailwind `darkMode: "class"`, a `ThemeContext` + toggle persisted to `localStorage`) applied platform-wide, not just the marketing site, plus a general visual polish pass (`AppLayout`, `Home`, a new `Footer`).
- **Credits and Marketplace split into two pages** (`/dashboard/credits`, `/dashboard/marketplace`) with a direct credit-purchase flow independent of subscribing to a plan (see Credits notes above), rather than one combined page conflating "buy from us" with "buy from another account."

### Production deployment: nginx reverse proxy + ngrok tunnel

The spec's own bonus deployment target is AWS (EC2/RDS via a `main`-branch release-PR pipeline); that wasn't pursued for this environment. Instead, the whole stack sits behind an **nginx reverse proxy**, unifying the frontend and every Gateway-proxied API route under one origin, tunneled to a public HTTPS URL by **ngrok** — enough to make LinkedIn's OAuth callback and Stripe's webhooks (both of which require a real, internet-reachable endpoint) work against a stack that's still actually running on a local machine.

- **`nginx/nginx.conf`** — an `upstream` each for `gateway:8000` and `frontend:5173`. Two real path collisions exist between the frontend's client-side SPA routes and the Gateway's API prefixes: both use `/admin` (the SuperAdmin console page vs. every `/admin/{path}` API call), and the frontend's entire `/dashboard/*` namespace overlaps the Gateway's one real endpoint at `GET /dashboard/summary`. Both are resolved with nginx's `location =` exact-match precedence — always checked before any prefix location regardless of declaration order — rather than depending on fragile prefix-block ordering that would silently break if the Gateway ever added a conflicting route. Every other Gateway prefix gets its own `location` block proxying to `gateway_upstream`; `/sse/` gets `proxy_buffering off` and a 3600s read timeout so AI generation's token stream isn't buffered into one delayed chunk; the catch-all `location /` proxies to the frontend with the `Upgrade`/`Connection` headers Vite's HMR websocket needs.
- **`VITE_API_BASE_URL` is empty by default** (was a hardcoded `http://localhost:8080`) so the frontend's `apiFetch` calls resolve as relative paths against whatever origin the browser actually loaded the page from — nginx on `:80` locally, or the public ngrok URL — instead of a fixed port that only works for direct, un-proxied access to the Vite dev server.
- **Two real deployment bugs, found getting the tunnel working end to end**: (1) a custom `entrypoint` override on the `ngrok` service (meant to conditionally pass `--domain`) bypassed the official image's own entrypoint handling, leaving the local inspection API bound to `127.0.0.1` inside the container regardless of the port mapping — and `--web-addr` isn't even a real flag on ngrok v3's `http` command, so the original approach would have failed either way. Fixed by dropping the custom entrypoint entirely and using `command: ["http", "nginx:80"]` directly, matching ngrok's own documented `docker run` usage. (2) Once the tunnel came up, Vite's dev server rejected every request through the public ngrok URL with a 403 ("Blocked request... add to `server.allowedHosts`") — its DNS-rebinding protection default-denies any `Host` header not on an explicit allowlist, and a rotating tunnel domain obviously isn't on one. Fixed with `allowedHosts: true` in `vite.config.ts` rather than hardcoding a domain the repo would need a code change to update every time the tunnel restarts.
- **Verified live, through the actual public URL, not just localhost**: the frontend loads, an unauthenticated API route correctly 401s, both collision-prone exact-match paths route correctly, and a real signup request completes end-to-end through nginx → Gateway → Auth → the rest of the platform.

#### Running it

1. Create a free account at [ngrok.com](https://ngrok.com) and copy your authtoken from the dashboard into `.env`'s `NGROK_AUTHTOKEN`. A static domain (Domains section of the dashboard, one free per account) is strongly recommended and goes in `NGROK_STATIC_DOMAIN` — without one, the public URL changes on every restart, breaking LinkedIn's registered redirect URI and any already-configured Stripe webhook endpoint.
2. `docker-compose up --build` — this now also brings up `nginx` (port `80`) and `ngrok` (its local inspection dashboard on port `4040`, at `http://localhost:4040`, shows the current public URL and every request/response passing through the tunnel).
3. Once a static domain is set, update `LINKEDIN_REDIRECT_URI` / `FRONTEND_CONNECTIONS_URL` / `FRONTEND_BASE_URL` in `.env` to that domain and register the matching redirect URI in the LinkedIn Developer App's own settings (an external site — this step can't be done programmatically). Registering a Stripe webhook endpoint against the new public URL is optional; local testing still works fine via `stripe listen`.
4. **This is now done and permanent, not just aspirational** (see Slice 15 below): the `ngrok` service's `command` pins `--url=https://${NGROK_STATIC_DOMAIN}`, using the free "dev domain" every ngrok account is issued — the public URL no longer rotates on restart, and `LINKEDIN_REDIRECT_URI`/`FRONTEND_CONNECTIONS_URL`/`FRONTEND_BASE_URL` are all set to it in this repo's own `.env`.

## Slice 15: SuperAdmin hardening, SMTP email, login integrity, and Content Studio auto-research

A grab-bag of post-launch fixes and features, each triggered by a real report or a real gap found while using the live deployment rather than by re-reading the spec — the same "chase what's actually broken" pattern the whole platform has followed since Slice 13.

### LinkedIn OAuth and the public URL

`LINKEDIN_REDIRECT_URI`/`FRONTEND_CONNECTIONS_URL`/`FRONTEND_BASE_URL` were still hardcoded to `localhost` even after Slice 14's nginx+ngrok deployment went in — meaning LinkedIn's OAuth callback and every verification/invite/receipt email link resolved to a URL that only works in a browser on the machine running the stack, breaking for every other user. Fixed by pointing all three at the public ngrok URL. That then exposed the real remaining gap: the tunnel had no `--url`/`--domain` pin, so the public hostname could change on any restart, silently re-breaking those same three env vars and the LinkedIn app's own registered redirect URI. Every free ngrok account is issued one permanent "dev domain" for exactly this reason — `docker-compose.yml`'s `ngrok` service now pins to it via `NGROK_STATIC_DOMAIN` and ngrok's current `--url` flag (`--domain` is deprecated, confirmed by a live warning when it was tried first). Verified live: the tunnel re-binds to the identical domain across a forced container recreate.

### SuperAdmin: a dedicated UI, and undeletable

Two real, separate problems surfaced testing the SuperAdmin account: it looked exactly like a regular tenant account (Dashboard, Content Studio, Billing, Credits all in the nav, "Role: Owner" in the header — none of which means anything for an account whose job is managing the platform, not using it as a business), and — found by actually trying it — it could be deleted through the ordinary self-service `DELETE /account` flow, which is exactly what happened to this project's own SuperAdmin account mid-session, requiring it to be manually recreated from scratch.

- **`AppLayout`** hides the entire regular tenant nav for `is_superadmin` accounts, leaving just **SuperAdmin Console** and the new **Users** page (see below); the header badge reads "Role: SuperAdmin" instead of "Role: Owner" plus a Free-plan badge that was never relevant to what a SuperAdmin does; the sidebar logo links to `/admin` instead of `/dashboard`.
- **`DELETE /account`** now rejects with `403 superadmin_protected` if the target user has `is_platform_admin` set, checked before it even asks for a password. `ProfilePage`'s Danger Zone shows an explanatory message instead of the delete form for these accounts, so the UI doesn't offer an action the backend will just reject.
- **A platform-wide user directory** (`GET /admin/users`, SuperAdmin-only; frontend page at `/admin/directory`, linked as "Users") — a flat list of every user on the platform (email, verified status, signup date) plus total platform revenue as one figure, deliberately *not* broken down by account/plan tier the way the existing account-centric console already is. Backed by a new `GET /internal/users` on Auth (mirrors the existing per-id lookup, just unfiltered). The frontend route is `/admin/directory`, not `/admin/users`, on purpose: that literal path string is already the backend API endpoint's own path, and nginx has no way to route the same exact path to two different upstreams (frontend page vs. API call) based on nothing but the URL — the same collision class the `/admin` and `/dashboard/summary` exact-match rules already exist to avoid, so a matching `location = /admin/directory` rule was added to `nginx.conf`.

### Login now actually enforces email verification

`POST /login` never checked `email_verified` at all — any account could log in immediately after signup whether or not the verification link had ever been clicked. This had gone unnoticed specifically because it never mattered much when Resend's sandbox mode could only deliver to one address anyway; once real SMTP delivery worked for everyone (see below), it became a real, exploitable gap rather than a theoretical one. Fixed with a check placed *after* password verification (not before — a wrong-password attempt gets the same `invalid_credentials` response either way, so this can't be used to probe whether an unverified account exists), returning `403 email_not_verified`. Rolling this out for real meant cleaning up every account created before the check existed: 11 unverified test accounts were deleted outright — canceling their real (if test-mode) Stripe subscriptions first, then removing their data across every schema that had any (billing, credits, usage, AI generation, content, scheduler, social publishing, and the account/membership rows themselves), not just the `auth.users` row — after taking a full `pg_dump` safety backup first.

### Resend → SMTP

Resend's free/sandbox tier only delivers to the single email address that owns the Resend account — confirmed via `notification_log` showing a `403` for every other real recipient the entire session, the exact "verify a domain to unlock this" tier limitation Resend's own error message describes. Verifying a domain wasn't something this project wanted to do for a local/dev setup, so `app/email_client.py` was rewritten around plain SMTP (`aiosmtplib`, matching the codebase's async style) instead — a normal SMTP account (Gmail's, configured here via an App Password) has no equivalent "verified recipient" restriction. `send_email()`'s signature didn't change, so `notify.py`'s idempotent send-and-log logic needed zero changes. Verified live: a real password-reset email and a real signup's verification + welcome email all now show `status=sent` with no error, replacing what were Resend `403`s moments earlier for the exact same flows.

### Refund, marketplace, and credit-purchase emails

Three more events that already had real publishers (Billing's outbox) but no Notification listener at all: `refund.issued`, `marketplace.payment_completed`, and `credits.purchase_completed`. A refund silently updated the database with no email telling the customer their money was back; a marketplace sale/purchase and a direct credit purchase were the same way. Added to the existing `billing_events` routing (three more routing keys on the same queue): the refunded account gets the amount back; a marketplace sale emails **both sides independently** (buyer gets a purchase confirmation, seller gets a sale confirmation, each keyed on a distinct `event_id:buyer`/`event_id:seller` suffix so `send_and_log`'s per-recipient dedup check doesn't treat one as a duplicate of the other); a credit purchase confirms the amount bought. Verified live against real inboxes. One duplicate-send was observed during testing specifically for the marketplace case (RabbitMQ redelivered the message before the first delivery's log write had committed) — this is the same pre-existing, already-documented send-before-log race every Notification handler has (see Slice 13's "gaps deliberately not fixed" above), not a new issue; the other two tests each sent exactly once.

### Content Studio: optional automatic web research

Content Studio gained exactly one addition — a checkbox, "Research the web first (no URL needed)" — that makes generation automatically pull in factual context about the topic before writing, without the user picking a URL themselves. Real general web search with no API key turned out not to be practically available: DuckDuckGo's free HTML results page (the usual no-key option) actively **CAPTCHA-challenges scripted requests**, confirmed directly while building this (a real dead end, not a guess) — a "Select all squares containing a duck" bot challenge came back on the very first request. Wikipedia's own API is the honest alternative: free, no key, explicitly documented for programmatic use once a descriptive `User-Agent` is set (Wikimedia's API etiquette policy 403s requests without one — also discovered directly), and it covers a wide range of factual/reference topics well. It's a real, worth-stating limitation of this feature that it won't help with current events, specific products, or anything Wikipedia has no article on — this was never oversold as "searches the whole web."

- **Scraper** gained `app/search.py` (search Wikipedia, fetch its intro extract) and `POST /internal/research` — service-to-service only, blocked from the public internet the same way every other `/internal/*` route already is.
- **AI Generation**'s `CreateGenerationRequest` gained `use_web_research: bool`; a new `app/scraper_client.py` calls the endpoint best-effort — a failed search/scrape just means generation proceeds without it, never fails the request — and `app/generation.py` folds a successful result in as context ahead of the user's actual prompt before it ever reaches Groq, while `PromptHistory` still stores the original, unaugmented prompt (what the user actually typed, not what Groq actually received).
- Verified live end to end: a real generation with the toggle on produced a real `POST /internal/research → 200` in Scraper's logs (confirmed it actually ran, not just that the model already knew the topic), returning a genuine Wikipedia extract that measurably became part of the prompt Groq received.
- **The standalone Web Scraper page was removed** as a direct follow-up — now that its core capability (fetching content automatically) is reachable from inside Content Studio, the separate "give me a URL to scrape" page was judged redundant for regular users. Only the frontend page and its nav link are gone; the Scraper backend service, its REST API (`/scrape-jobs` etc.), and the async recurring-job flow described in the Scraper Service notes above are all untouched — Content Studio's research toggle depends on that same service's new `/internal/research` endpoint, just not the old page that drove the old flow.

### Calendar now shows what was actually scheduled

The calendar's day cells and its "Schedule content for `<date>`" detail panel only ever showed the scheduled time and status — never what was actually scheduled, since `GET /scheduled` only returns `content_id` (a deliberate Scheduler-side scope decision from Slice 7, to avoid an N+1 fan-out to Content per calendar render). No backend change needed: the frontend already fetches the account's full content list for the "Choose content..." dropdown, just immediately filtered down to approved-only and discarded. Kept the full unfiltered list alongside the approved-only one and built a lookup so both the grid and the detail panel can resolve any scheduled post's real title (and a short body preview in the detail panel) — including already-fired or cancelled posts, which the approved-only list alone would have excluded.

## Roadmap (remaining work)

- **AWS deployment** (the spec's own bonus deployment target, via a `main`-branch release-PR pipeline) was not pursued for this environment in favor of the nginx + ngrok tunnel above, which better fits a stack that's still actually running on a local machine rather than provisioned cloud infrastructure.
- The two acknowledged, deliberately-not-fully-closed idempotency gaps from Slice 13 (Social Publishing's LinkedIn post, Notification's email send — both since partially mitigated, see that section and Slice 15 above) remain the platform's only known at-least-once-not-exactly-once side effects.

Git workflow: `main` (protected, production) / `dev` (protected, integration) / `feature/*` / `fix/*`, PR + at least one review + passing CI (added in the Slice 14 audit above) before merge into `dev`; this project's actual working pattern has been a `feature/<name>`/`fix/<name>` branch off `dev`, a detailed commit, then a `--no-ff` merge back into `dev` for every change described in this document. **`main` now receives full `--no-ff` merges from `dev`** (not just a periodic README-only sync, which was the earlier pattern through Slice 14) — a full `main`-branch release/deployment pipeline (the spec's original framing for what `main` triggers, e.g. gating on CI passing before the merge) was still not built, so this is a manually-triggered full sync rather than an automated release process. Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, ...) throughout.
